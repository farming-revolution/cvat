---
title: Track height diagnostic
---

The ⓘ control on a point track estimates its vertical projection height. It never
saves annotations, changes camera settings, joins tracks or updates synchronization
baselines. Locked tracks are supported. Multipoint tracks are not.

Correct the track before interpreting the estimate: generated, uncorrected tracks
can reproduce the projection assumption that generated them. This is not an
independent camera calibration. There is no Apply action.

The dialog uses current, unsaved keyframes and recomputes whenever opened. An
annotation update while it is open marks the result outdated; choose Recalculate.
Outside, occluded, deleted-frame and out-of-image observations are excluded.
Frame deletion/restoration uses the current cached job state, including unsaved changes.
Interpolation does not create observations. Native normal and Ignore tracks are
always estimated separately. Tracks crossing recordings are refused.

## Calculation

The implementation follows `weeding_recording.cvat_projection.project_ground_points`:
reconstruct target Z from the camera-plane constraint, including camera tilt; use
the fixed horizontal projection reference for U and candidate vertical height for
V. At each candidate height, solve the shared target X/Y by linear least squares.
Search logarithmically over 0.05–10 m, then refine by golden-section minimization.
The objective is mean squared two-dimensional pixel distance (RMS is its square
root). Reject boundary minima, singular geometry and locally flat height profiles.

The dialog reports centimetres, observation count, frame range and RMS error.
Warnings accompany fewer than three keyframes, under 20 px vertical movement or
RMS above 5 px. Two observations may determine a height but offer little evidence
about its accuracy. Poor fits remain visible with warnings; missing/degenerate
information produces an explanation without a numeric estimate.

## Optional metadata contract, version 1

`GET /api/tasks/{id}/height-diagnostic` returns task/data IDs and an SHA-256
fingerprint of exact frame names, order, dimensions, frame step and deleted frames.
`PUT` at the same endpoint uploads `{version, task_id, data_id, frame_fingerprint,
bag: {bag_id, target_frame, horizontal_height_m, frames}}`. Each frame contains
its annotation index, exact name/dimensions, projection (12 values) and
row-major target-to-camera transform (16 values).

`GET /api/jobs/{id}/height-diagnostic` returns only the job's frame subset and
validated bag projections, or a missing/stale/invalid status. It uses existing job
data permissions. Task GET/PUT use existing task metadata read/update permissions.
The endpoints require the normal CVAT authentication and organization access.

Storage is `height-diagnostic.json` in the persistent task directory, separate
from annotation formats, labels and model rows. PUT locks task/data identity and
the file, validates finite geometry and mappings, preserves other bags, rejects
frame ownership overlaps, and atomically replaces the file. Repeated identical
uploads do not rewrite it. A changed frame catalogue disables reading until a fresh upload revalidates
the current mapping; other bags are retained only if their exact mappings still
validate. Inconsistent mappings and changed task/data identities reject the upload. Corrupt files require administrator
inspection rather than silently discarding another bag. No task timestamps or
annotation revisions are saved. No migration is needed.

The worker enriches successful creation and synchronization, including no-change
syncs, from the validated projection cache. Optional endpoint failures produce a
warning and are retried only on the next user-requested sync. No historical job or
annotation is automatically recreated. Legacy workers remain supported.

The UI shares one metadata request per job, revalidates on focus (30 s throttle)
and before opening, and performs no metadata request or fit during frame changes.
Absent/old endpoints disable the control without affecting editing or saving.

## Validation and rollback

Numerical fixtures are generated by the Python worker projector using
`tests/unit/fixtures/generate-height-projection.py`; they include tilt, independent
horizontal height, weak motion and near-boundary heights. Node tests cover
invalid/mixed-bag data, endpoint-only tracks, noisy fits, edits and shared requests.
Storage and isolated-server tests cover atomic/concurrent/idempotent uploads,
permissions, job frame steps and unchanged model saves.

Deploy backend first, then UI; keep prior images, configuration and UI assets.
Existing jobs and annotations require no migration. Older workers ignore the file;
older servers disable the new UI control. An annotation rollback is never needed.

Validated on 2026-10-12: 70 Node tests, eight isolated backend tests, UI TypeScript
and changed-file lint checks, and the production UI build passed. Browser tests
used existing task reads with all network writes blocked and local diagnostic
responses; they verified legacy/locked tracks, unsaved edits and frame deletion/restoration, undo, outdated
results and unchanged annotation exports. Four serial baseline/new/new/baseline
runs on Arnika (3721) and weed enrichment (3699) found no repeatable frame-switch
regression and no per-frame metadata requests. Pooled cached-pass medians were
112→102 ms and 287→253 ms respectively (24 transitions per variant/task);
these measurements establish no regression, not a claimed speed improvement.

Review fixes: deleted keyframes no longer define the diagnostic's visible track
span, matching CVAT interpolation when checking recording boundaries. A job with
no matching projection frames stays disabled even if another job in the same task
has metadata. These checks do not change annotations or stored metadata and run
only when opening the diagnostic or refreshing its shared metadata.

Regression validation: 73 Node tests, nine isolated backend tests, TypeScript,
changed-file lint checks and the production UI build passed.
